# EA_IDR_RISK_PROTECTION_SPEC

## 1. Project Identity

**Project:** EVE IDR Risk Protection EA  
**Platform:** MetaTrader 5 (MQL5)  
**Primary broker/account context:** Exness Pro  
**Account currency:** IDR / Rupiah  
**Primary purpose:** Account-wide floating-loss protection, configurable floating-profit auto-close, and aggregate monetary-risk Stop Loss management.

> This EA is a **risk-protection / trade-management system**, not a signal generator. It must not open trades by itself.

---

## 2. User's Core Requirements

The EA must satisfy these requirements exactly:

1. All configurable monetary thresholds must be expressed in **IDR / Rupiah**, not USD.
2. The user must be able to enter any nominal amount desired, e.g.:
   - Rp100,000
   - Rp250,000
   - Rp500,000
   - Rp1,000,000
   - Rp2,500,000
   - Rp10,000,000
   - or any other valid IDR amount supported by the implementation.
3. **Global Floating Loss Protection** must monitor the floating profit/loss of **all open positions in the trading account**.
4. The floating-loss calculation must use **position floating profit only**.
   - Include: `POSITION_PROFIT`.
   - Exclude: swap.
   - Exclude: commission.
   - Do not add external conversion costs or other fees to the trigger calculation.
5. When total floating loss reaches or exceeds the configured limit, the EA must automatically attempt to **close all open positions in the account**.
6. Trigger condition for global floating loss must be:
   - `TotalFloatingProfitIDR <= -MaxGlobalFloatingLossIDR`
   - Use threshold-crossing logic, not equality-only matching, because price moves in ticks and execution is asynchronous.
7. **Global Floating Profit Auto-Close** must monitor the same account-wide floating P/L and automatically close all open positions when the configured positive IDR profit target is reached or exceeded.
8. The floating-profit calculation must use **position floating profit only** (`POSITION_PROFIT`), with no swap or commission added.
9. The floating-profit target must be independently configurable in **IDR/Rupiah** and independently switchable ON/OFF.
10. The profit trigger must be:
   - `TotalFloatingProfitIDR >= GlobalFloatingProfitTargetIDR`
   - Use threshold-crossing logic, not equality-only matching.
11. After global protection triggers, the EA must be able to enter a **LOCKED / PROTECTION** state.
8. The post-trigger lock behavior must be **configurable ON/OFF**.
9. When LOCKED mode is ON, the EA must require a **manual reset** before it becomes ARMED again.
10. The user also wants an **automatic Stop Loss engine** that can assign SLs to entries according to one aggregate IDR loss budget.
11. The SL engine must be individually configurable **ON/OFF**.
12. When several positions are open, the SL engine must distribute the configured maximum total loss across those positions so that the **aggregate theoretical loss at the assigned SL levels does not exceed the configured IDR risk budget**, subject to broker limitations and execution reality.
13. The EA must support multiple entries and must not assume only one position exists.
14. The EA must work with manually opened trades and EA-generated trades; do not rely only on magic number unless a scope filter is explicitly enabled.
15. The EA must be safe after MT5/VPS restart: it must inspect current positions and restore its protection state from persistent state where possible.

---

## 3. Important Interpretation of "All Positions"

For the first implementation, **ALL POSITIONS means every currently open position in the account**, regardless of:

- symbol
- magic number
- comment
- whether the position was manual or generated by another EA
- BUY or SELL

Therefore, if the account contains:

```text
BUY XAUUSD     -Rp200,000
BUY XAUUSD     -Rp150,000
SELL EURUSD   -Rp100,000
BUY GBPUSD     -Rp80,000
------------------------------------------------
Total          -Rp530,000
```

and the limit is Rp500,000, the Global Floating Loss Protection must trigger and attempt to close **all four positions**.

This behavior must be prominently documented in the EA input panel so the user cannot accidentally assume the EA only protects XAUUSD.

> Do not silently change this scope to "current symbol" or "EA magic number".

The implementation must not hard-code USD.

At initialization, read:

```mql5
AccountInfoString(ACCOUNT_CURRENCY)
```

Expected value:

```text
IDR
```

The EA must validate this at startup.

### Currency mismatch behavior

If account currency is not IDR:

2. Write a critical journal log.
3. Do not perform automatic monetary-risk calculations using a guessed conversion rate.
4. Do not silently convert using a hard-coded USD/IDR exchange rate.
5. The EA should enter a SAFE_DISABLED state until the user corrects the account/setting.

No web FX conversion is required for the intended Exness Pro IDR account.

# 5. Feature A — Global Floating Loss Protection

## 5.0 Monitoring architecture — mandatory

The global loss monitor must **not rely on `OnTick()` alone**. The EA may be attached to XAUUSD while the account also contains other symbols, and the attached symbol may temporarily have no tick.

Required monitoring layers:

1. `OnTick()` for fast reaction when ticks arrive.
2. `OnTimer()` for periodic account-wide reconciliation, regardless of the attached chart symbol.
3. `OnTradeTransaction()` for immediate position-set changes.

Recommended timer interval: configurable, default **250 ms**, subject to platform limits and practical CPU/network load. The timer is a safety/reconciliation mechanism, not a guarantee of zero latency.

The EA must never claim that a threshold is executed at the exact nominal amount. Market movement, tick arrival, terminal latency, and broker execution can cause realized loss to exceed the threshold. The specification controls the trigger and the close attempt, not the exact realized fill price.


## 5.1 Inputs

Minimum required inputs:

```text
EnableGlobalFloatingLossProtection = true/false
MaxGlobalFloatingLossIDR            = user-defined amount
LockAfterGlobalTrigger              = true/false
RequireManualReset                  = true/false (must be true if LockAfterGlobalTrigger=true)
CloseRetryCount                     = configurable integer
CloseRetryDelayMs                  = configurable integer
VerificationTimeoutMs              = configurable integer
```

Recommended defaults:

```text
EnableGlobalFloatingLossProtection = true
MaxGlobalFloatingLossIDR            = 500000
LockAfterGlobalTrigger              = true
RequireManualReset                  = true
CloseRetryCount                     = 5
CloseRetryDelayMs                  = 250
VerificationTimeoutMs              = 5000
```

The user must be able to change the IDR amount from the MT5 Inputs tab without recompiling the EA.

---

## 5.2 Floating-loss calculation

Compute:

```text
TotalFloatingProfitIDR = sum(POSITION_PROFIT for all open positions)
```

Do **not** add:

```text
POSITION_SWAP
commission
```

for the purpose of this trigger.

The calculation must be based on live account positions, not historical deals.

Pseudocode:

```text
TotalFloatingProfitIDR = 0

for each open position:
    TotalFloatingProfitIDR += PositionGetDouble(POSITION_PROFIT)
```

Then:

```text
FloatingLossIDR = max(0, -TotalFloatingProfitIDR)
```

Trigger:

```text
if EnableGlobalFloatingLossProtection
   and FloatingLossIDR >= MaxGlobalFloatingLossIDR
then
   TriggerGlobalProtection()
```

Equivalent trigger logic is:

```text
TotalFloatingProfitIDR <= -MaxGlobalFloatingLossIDR
```

Use a valid positive limit. Reject zero/negative limits where appropriate.

# 5A. Feature B — Global Floating Profit Auto-Close

## 5A.1 Objective

The EA must support an independent **global floating-profit target** expressed only in **IDR/Rupiah**.

Example:

```text
Global Floating Profit Auto-Close = ON
Target = Rp500.000

P1 XAUUSD   +Rp250.000
P2 XAUUSD   +Rp180.000
P3 XAUUSD   +Rp90.000
-----------------------
Total       +Rp520.000

=> CLOSE ALL POSITIONS
```

The comparison is based on the **net sum of `POSITION_PROFIT` across all open positions in account scope**.

Do not include:

```text
POSITION_SWAP
commission
```

for this profit trigger.

## 5A.2 Inputs

```text
EnableGlobalFloatingProfitAutoClose = true/false
GlobalFloatingProfitTargetIDR       = user-defined positive amount
LockAfterGlobalProfitTrigger        = true/false
RequireManualResetAfterProfit       = true/false (must be true if LockAfterGlobalProfitTrigger=true)
```

The user must be able to change the target from the MT5 Inputs tab without recompiling.

Every monetary input and every monetary display must remain in **IDR/Rupiah**.

## 5A.3 Calculation

```text
TotalFloatingProfitIDR = sum(POSITION_PROFIT for all open positions)
```

For the intended Exness Pro IDR account, there must be **no USD conversion** and no hard-coded FX rate.

Trigger condition:

```text
if EnableGlobalFloatingProfitAutoClose
   and TotalFloatingProfitIDR >= GlobalFloatingProfitTargetIDR
then
   TriggerGlobalProfitProtection()
```

A positive target is required. Reject zero/negative targets when the feature is enabled.

The target is based on **account-wide net floating profit**, so profitable and losing positions offset each other.

For dashboard purposes:

```text
FloatingProfitIDR = max(0, TotalFloatingProfitIDR)
```

Do not calculate the target from the sum of only winning positions.

## 5A.4 Close-all behavior

When the profit target is reached:

1. Transition to a protection-triggered state with reason `GLOBAL_FLOATING_PROFIT_TARGET`.
2. Snapshot all open positions currently in account scope.
3. Attempt to close **all open positions in the account**, not only profitable positions.
4. Re-enumerate positions after each close batch.
5. Retry bounded failures.
6. Verify that positions are actually closed.
7. If new positions appear during the close operation, they must be treated as part of the same close-all event.
8. After all positions are verified closed:
   - if `LockAfterGlobalProfitTrigger=true`, enter `LOCKED`;
   - otherwise return to `ARMED`.

The EA must never close only the winning positions because the configured requirement is an **account-wide close-all** at the target.

## 5A.5 Profit-trigger lock behavior

Profit-trigger locking is independently configurable from loss-trigger locking.

Recommended default:

```text
LockAfterGlobalProfitTrigger = false
```

If enabled:

```text
GLOBAL PROFIT TRIGGER
        -> CLOSE ALL
        -> LOCKED
        -> manual reset
        -> ARMED
```

If disabled:

```text
GLOBAL PROFIT TRIGGER
        -> CLOSE ALL
        -> ARMED
```

If `LockAfterGlobalProfitTrigger=true`, `RequireManualResetAfterProfit` must be true and a manual reset is required before returning to ARMED.

## 5A.6 Interaction with global floating-loss protection

The two thresholds are independent and act on the same account-wide `POSITION_PROFIT` aggregation:

```text
TotalFloatingProfitIDR <= -MaxGlobalFloatingLossIDR
        -> GLOBAL FLOATING LOSS PROTECTION

TotalFloatingProfitIDR >= GlobalFloatingProfitTargetIDR
        -> GLOBAL FLOATING PROFIT AUTO-CLOSE
```

If either trigger is already active, the other trigger must not reset, override, or cancel the ongoing close-all operation. The protection reason must remain explicit:

```text
GLOBAL_FLOATING_LOSS
GLOBAL_FLOATING_PROFIT_TARGET
```

## 5A.7 Threshold is not an exact realized-profit guarantee

A target such as Rp500.000 is a **trigger threshold**, not a guarantee that final realized closed profit will equal exactly Rp500.000. Final realized profit can differ because of market movement, spread, slippage, execution latency, partial fills, and sequential closing of multiple positions.

# 6. Shared Global Close-All Action

When either global floating-loss protection **or** global floating-profit auto-close triggers:

1. Transition state to `PROTECTION_TRIGGERED`.
2. Snapshot all open positions that were detected at trigger time.
3. Attempt to close **all positions in account scope**.
4. Verify each position has actually disappeared/closed.
5. Retry failures according to configured retry policy.
6. Continue monitoring the account while closing.
7. Do not assume a sent close request means a successful close.
8. After all positions are verified closed:
   - if `LockAfterGlobalTrigger = true`, enter `LOCKED`;
   - otherwise return to `ARMED`.

### Close ordering

Preferred implementation:

- close positions one by one with verification;
- after each batch, re-enumerate positions;
- continue until no positions remain or the retry policy is exhausted.

The system must handle both hedging and netting account behavior appropriately.

Use documented MT5 trade APIs and broker-supported filling mode.

# 7. Feature C — Lock / Protection Mode

## 7.1 Purpose

After an emergency global-loss close, the system can remain locked to prevent immediate re-exposure.

### Lock ON behavior

When:

```text
LockAfterGlobalTrigger = true
```

then after successful close-all:

```text
STATE = LOCKED
```

The EA must not transition back to ARMED automatically.

### Manual reset

Provide a clear mechanism for manual reset, for example:

- an MT5 chart button `RESET PROTECTION`, and/or
- an input flag such as `ManualReset = true` followed by a controlled reset event.

Preferred implementation: a chart button, because it avoids repeated property edits/reinitialization.

After successful reset:

```text
LOCKED -> ARMED
```

Only allow reset when there are no protected positions remaining, or make the behavior explicit and safe.

### Pending orders while LOCKED

The current requirement is defined for **open positions**, not pending orders. Pending orders must not be silently treated as positions.

However, because a pending order can create a new position after the account has entered LOCKED state, the EA must expose an explicit safety input:

```text
CancelPendingOrdersWhenLocked = true (default)
```

When enabled, after entering LOCKED the EA must attempt to delete all pending orders in the account, verify deletion, retry bounded failures, and log the result. This prevents an already-placed pending order from reintroducing exposure after the emergency lock.

If disabled, pending orders remain untouched and this limitation must be shown clearly on the dashboard.

### Lock OFF behavior

When:

```text
LockAfterGlobalTrigger = false
```

then after all positions are closed and the trigger condition is no longer active:

```text
PROTECTION_TRIGGERED -> ARMED
```

The EA may continue monitoring new positions.

### Important note

This risk EA cannot prevent a separate EA or a human from sending a new order at the platform level. If `LOCKED` and a new account position appears, the implementation must have a clearly defined policy.

Recommended policy:

```text
LOCKED + new position detected
            -> immediately attempt to close the newly detected position
            -> keep LOCKED state
            -> log the event
```

This should be configurable if technically feasible, but the safe default is to reject/close new exposure while locked.

# 8. Feature D — Aggregate IDR Stop Loss Engine

## 8.1 Objective

The user wants the EA to set an SL on each entry such that the **combined theoretical loss across all protected positions at their respective SL prices is constrained by one configurable IDR risk budget**.

Example:

```text
Configured total SL risk budget = Rp500,000

Position 1 = 0.10 lot
Position 2 = 0.20 lot
Position 3 = 0.30 lot

Total lots = 0.60

Risk allocation proportional to volume:
P1 ≈ Rp83,333
P2 ≈ Rp166,667
P3 = Rp250,000

Aggregate theoretical SL loss ≈ Rp500,000
```

The exact monetary SL calculation must use broker/symbol contract specifications rather than assuming a fixed value per point.

---

## 8.2 Inputs

Minimum required inputs:

```text
EnableAggregateIDRSL             = true/false
MaxAggregateSLRiskIDR             = user-defined amount
AutoApplySLToNewPositions         = true/false
RebalanceExistingPositionsOnNewEntry = true/false
SLAllocationMethod                = PROPORTIONAL_TO_VOLUME (default)
PreserveMoreProtectiveExistingSL = true/false
FailSafeWhenCompliantSLImpossible = CLOSE_POSITION / LEAVE_UNPROTECTED
```

Recommended defaults:

```text
EnableAggregateIDRSL                  = true
MaxAggregateSLRiskIDR                 = 500000
AutoApplySLToNewPositions              = true
RebalanceExistingPositionsOnNewEntry   = true
SLAllocationMethod                     = PROPORTIONAL_TO_VOLUME
PreserveMoreProtectiveExistingSL      = true
FailSafeWhenCompliantSLImpossible     = CLOSE_POSITION
```

# 9. Aggregate SL Allocation Logic

## 9.1 Risk budget is a ceiling, not a target

`MaxAggregateSLRiskIDR` is a **maximum theoretical loss budget**. The EA must never intentionally widen stops merely to consume the entire budget. A lower aggregate risk is always acceptable.

The default planning method may use proportional allocation by volume, but the final SLs must be validated against actual broker/symbol economics.

For position `i`:

```text
RiskWeight_i = Volume_i / TotalVolume
AllocatedRisk_i = MaxAggregateSLRiskIDR * RiskWeight_i
```

Rounding must use integer IDR units and the final sum of allocated budgets must not exceed `MaxAggregateSLRiskIDR`.

## 9.2 Existing SLs are safety constraints

When a position already has an SL:

- If the existing SL is **more protective** than the newly calculated basket SL, preserve it by default.
- Never move an SL farther from the current market merely to equalize the nominal allocation unless the user explicitly disables preservation and the resulting aggregate theoretical risk remains within budget.
- A tighter existing SL reduces aggregate risk and is therefore always acceptable.

For BUY positions, a lower SL price is farther/riskier and a higher SL price is more protective.
For SELL positions, a higher SL price is farther/riskier and a lower SL price is more protective.

## 9.3 Basket recalculation

When positions are added, removed, partially closed, or materially changed, the EA must reconcile the basket. If `RebalanceExistingPositionsOnNewEntry=true`, recalculate the basket risk plan.

**Critical invariant:** the EA may tighten stops to bring aggregate theoretical risk down, but must not loosen existing stops in a way that increases aggregate risk beyond the configured budget.

If the current basket is already below budget because of protective existing SLs, do not widen stops just to use the remaining budget.

# 10. Converting an IDR Risk Allocation into an SL Price

Do not use a simplistic points/pips formula. Use MT5 symbol/account calculation facilities, principally `OrderCalcProfit()` where supported, with the account's actual currency.

For each position, solve for the furthest **legal** SL that keeps theoretical loss at or below the allocated IDR budget, subject to the position direction. A binary search or another numerically stable bounded solver may be used.

### BUY

```text
SLPrice < Current/Reference Price
abs(OrderCalcProfit(ORDER_TYPE_BUY, symbol, volume, referencePrice, SLPrice))
    <= AllocatedRiskIDR
```

### SELL

```text
SLPrice > Current/Reference Price
abs(OrderCalcProfit(ORDER_TYPE_SELL, symbol, volume, referencePrice, SLPrice))
    <= AllocatedRiskIDR
```

The reference price for the **aggregate SL loss budget** must be the position's **open price (`POSITION_PRICE_OPEN`)**, because the user's requirement is to cap the total loss from each entry to the configured IDR budget. Do not substitute current BID/ASK for the entry price when calculating the theoretical loss budget.

Current BID/ASK may still be used to validate whether the SL is on the correct executable side of the market and whether broker stop/freeze constraints are currently satisfied.

Normalize candidate prices to `SYMBOL_TRADE_TICK_SIZE`, then validate against `SYMBOL_DIGITS`. Do not rely on decimal digits alone when tick size differs from point size.

The theoretical SL loss calculation is an estimate from `POSITION_PRICE_OPEN` to the SL price. It cannot guarantee realized loss because of gaps, slippage, execution rejection, and market discontinuity.

# 11. Broker Constraints for SL

Before sending/modifying an SL, validate at minimum:

- `SYMBOL_TRADE_STOPS_LEVEL`;
- `SYMBOL_TRADE_FREEZE_LEVEL`;
- `SYMBOL_TRADE_TICK_SIZE`;
- `SYMBOL_DIGITS`;
- trade mode;
- volume validity;
- symbol trading/session status;
- supported filling/execution mode.

## 11.1 Unsatisfiable risk condition

If the closest legal SL would already imply theoretical loss **greater than the allocated IDR budget**, the EA must **not** place that oversized-risk SL and must not report the position as protected.

Required behavior:

1. Log `CRITICAL_SL_BUDGET_UNSATISFIABLE`.
2. Display symbol, ticket, volume, allocated budget, closest legal SL, and calculated theoretical loss.
3. Keep Global Floating Loss Protection active.
4. Apply the configured fail-safe policy:

```text
FailSafeWhenCompliantSLImpossible = CLOSE_POSITION (default)
```

If `CLOSE_POSITION` is enabled, attempt to close the affected position because the requested hard risk boundary cannot be represented by a broker-valid SL. If disabled, leave the position open but mark it **UNPROTECTED** and raise a persistent critical alert.

The EA must never silently widen the stop beyond the configured budget.

## 11.2 SL modification failure

If an SL modification is rejected:

- retry only according to a bounded retry policy;
- re-read the position before retrying;
- never send duplicate blind modifications;
- if the position remains unprotected, apply the fail-safe policy and log the exact broker retcode.

# 12. New Position Detection

The EA must detect new positions regardless of whether they were opened manually or by another EA.

Required mechanisms:

- `OnTradeTransaction()` for immediate trade/position changes;
- `OnTimer()` for periodic full reconciliation;
- `OnTick()` only as an additional low-latency path.

The EA must not rely only on the current chart symbol.

When a new position appears and `EnableAggregateIDRSL=true` + `AutoApplySLToNewPositions=true`, recalculate the risk plan and attempt to apply a compliant SL.

---

# 13. Dynamic Basket Rebalance

When the protected position set changes, the EA must reconcile the aggregate SL plan.

The following events must trigger reconciliation:

- new position;
- position close;
- partial close;
- position volume change;
- manual SL change;
- EA SL modification;
- symbol price movement sufficient to affect the risk calculation;
- terminal/VPS restart.

Reconciliation must be idempotent: running it repeatedly without a material change must not generate unnecessary trade modifications.

### Safe rebalance algorithm

1. Snapshot all in-scope positions.
2. Read current SLs.
3. Calculate the basket risk budget.
4. Preserve existing more-protective SLs when configured.
5. Calculate required SLs only for positions whose protection is missing or insufficient.
6. Tighten stops where necessary to satisfy the budget.
7. Never widen an existing stop merely to redistribute risk.
8. Verify each resulting SL against broker constraints and `OrderCalcProfit()`.
9. If the basket cannot be made compliant, invoke the fail-safe policy for affected positions.
10. Re-read positions after modifications and verify the final state.

### Important limitation

An SL is not a guaranteed monetary cap. The aggregate budget means **theoretical loss at the configured SL prices under MT5's calculation model**. Gaps and slippage can produce larger realized losses. Global Floating Loss Protection remains the emergency backstop.

# 14. Interaction Between Aggregate SL and Global Floating-Loss Protection

These are two independent protections.

## Aggregate SL

Purpose:

```text
Protect each position / basket from reaching the configured theoretical SL loss.
```

## Global Floating-Loss Protection

Purpose:

```text
Emergency account-wide floating loss cutoff.
```

Recommended architecture:

```text
                ACCOUNT POSITIONS
                       |
          +------------+------------+
          |                         |
          v                         v
   AGGREGATE SL ENGINE      GLOBAL LOSS MONITOR
          |                         |
          v                         v
       Per-position SL         CLOSE ALL
                                      |
                                      v
                                   LOCKED
```

The global loss cutoff is the emergency backstop and must remain functional even if one or more SL operations fail.

# 15. Do Not Create a Trading Strategy

The EA must NOT:

- open BUY orders on its own;
- open SELL orders on its own;
- generate technical-analysis signals;
- use MA/RSI/MACD/etc. to decide entry;
- perform martingale;
- perform grid recovery;
- average down;
- increase position size to recover a loss;
- use hidden orders for recovery;
- override user-defined risk limits.

This project is purely a **risk-control EA**.

# 15A. Account-Wide Monitoring Invariant

Because this EA protects the **entire account**, all position enumeration functions must iterate the full position pool (`PositionsTotal()` / `PositionGetTicket()` / appropriate selection APIs), not only positions for `_Symbol`.

A timer reconciliation is mandatory. The EA must remain effective when the chart symbol has no tick.

The timer must also detect positions opened by other EAs while the current chart receives no ticks.

Recommended states:

```text

  |
  v
VALIDATING
  |
  +--> SAFE_DISABLED   (invalid currency/configuration)
  |
  v
ARMED
  |

  |       (LOSS or PROFIT TARGET)

  |             |
```

# 17. Persistent State

Because the EA may run on a VPS and MT5 may restart, the implementation must persist enough state to prevent an accidental auto-unlock after a restart.

Recommended mechanisms:

- terminal Global Variables;
- or a small local state file if necessary and safe.

Persist at minimum:

```text
Lock state
Last protection trigger time
Last trigger reason (LOSS / PROFIT TARGET)
Configuration checksum/version
```

On restart:

- if persistent state indicates `LOCKED`, restore `LOCKED` unless a deliberate manual reset occurs;
- reconcile current open positions;
- if protection was triggered but positions remain, continue closing logic.

# 18. Manual Reset Design

Preferred UX:

A chart button:

```text
[ RESET PROTECTION ]
```

When pressed:

1. Confirm the request via a clear chart message.
2. Verify no unresolved global close operation is active.

5. Recalculate SL protection if enabled.
6. Return state to `ARMED`.

# 22. Precision and Rounding

The configured nominal should be accepted as an integer-like IDR amount, but calculations may use floating-point values internally.

The implementation must:

- avoid binary-floating-point surprises in threshold comparisons where practical;
- normalize SL prices to symbol tick size;
- account for volume step;
- avoid accidental rounding that increases risk beyond the configured limit.

When a rounding decision could increase monetary risk, round toward **lower risk**, not higher risk.

---

# 23. Execution Reliability

All trade operations must inspect the MT5 trade result.

For every modification/close:

1. Send trade request.
2. Check return code.
3. Log result.
4. Re-query the position.
5. Verify desired state.
6. Retry if retryable.
7. Stop retrying if a fatal condition is detected.

Do not implement blind fire-and-forget trade commands.

# 25. Race Conditions / Edge Cases

The implementation must explicitly handle:

### A. Multiple positions appear in the same tick
Reconcile the entire basket before finalizing the SL plan.

### B. Price gaps/slippage
The actual close loss may exceed the trigger threshold. This is normal execution risk and must not be represented as an implementation guarantee.

### C. One position closes before the EA recalculates
Re-scan positions and rebuild the basket risk plan.

### D. New position is opened during CLOSE_ALL
Attempt to close it as part of the same protection event and keep the account in protection state.

### E. Broker rejects SL modification
Keep global protection active, log the rejection, and retry only where appropriate.

### F. Terminal restarts during closing
Restore persistent `PROTECTION_TRIGGERED` / closing state and resume reconciliation.

### G. No positions exist
Dashboard should show zero positions and no fake risk.

### H. Global floating loss becomes negative again after an attempted close
Continue closing until no in-scope positions remain or a defined unrecoverable condition exists.

### I. Locked state and manual trading
A newly detected position while locked should be handled according to the configured lock policy. Safe default: immediately close it and remain locked.

### J. Broker minimum stop distance makes requested risk impossible
Do not widen beyond the configured budget just to create an SL. Mark the position as `SL_UNSATISFIABLE` and rely on global protection.

# 26. Important Limitation: Threshold Is Not an Exact Execution Guarantee

The EA must explicitly document:

> A configured limit such as Rp500,000 is a trigger threshold, not a guarantee that the final realized loss will be exactly Rp500,000.

Reasons include:

- market movement between ticks;
- spread;
- slippage;
- execution latency;
- requotes/rejections where applicable;
- gaps;
- broker execution rules;
- minimum SL distance;
- partial execution/fills;
- multiple positions being closed sequentially.

The software's responsibility is to trigger as close as reasonably possible, execute robustly, and verify outcomes.

# 33. Acceptance Criteria

The implementation is not complete until all of the following are true:

### Monetary display

- All user-facing money is IDR/Rupiah.
- User can change thresholds without recompiling.
- No USD hard-coded anywhere in the risk logic.

### Global loss protection

- Monitors all open account positions.
- Uses only `POSITION_PROFIT` for global floating-loss trigger.
- Trigger uses threshold crossing, not equality-only.
- Attempts to close all positions.
- Verifies closure.
- Retries failed closes.

### Global floating-profit auto-close

- ON/OFF configurable.
- Target is configurable in IDR/Rupiah.
- Uses only `POSITION_PROFIT`.
- Excludes swap and commission.
- Uses account-wide net floating P/L.
- Trigger uses `>= target`, not equality-only.
- Closes all account positions, not only profitable positions.
- Verifies closure and retries failures.
- Profit-trigger lock behavior is independently configurable.

### Lock

- ON/OFF configurable.
- Manual reset works.
- Lock state survives restart where possible.
- Safe behavior for new positions during locked state.

### Aggregate SL

- ON/OFF configurable.
- Automatically detects new entries.
- Assigns individual SLs.
- Aggregate theoretical loss is constrained by the configured IDR budget.
- Handles multiple volumes.
- Handles BUY and SELL.
- Respects broker stop/freeze/tick-size constraints.
- Does not silently exceed the configured risk budget.

### Reliability

- Uses `OnTradeTransaction()` plus reconciliation.
- Has explicit state management.
- Has clear logs.
- No martingale/grid/recovery.
- No signal-generation logic.
